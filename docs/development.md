# Development

## Toolchain

- Python 3.12
- Node.js 24.18.0 (`>=24.18.0 <25`; use the repository `.nvmrc`) and npm
- Rust stable compatible with the `rust-version` in `frontend/src-tauri/Cargo.toml`
- Tauri platform prerequisites

Install exactly the locked dependencies:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install --require-hashes -r requirements-dev.lock
.venv\Scripts\python.exe -m pip install --no-build-isolation --no-deps --editable .
.\.venv\Scripts\Activate.ps1
npm ci --prefix frontend
```

Desktop sidecar packaging uses the separate, hash-locked `requirements-tooling.lock`. Regenerate
locks only from their reviewed input files:

```powershell
.venv\Scripts\python.exe -m piptools compile --generate-hashes --output-file requirements.lock requirements.txt
.venv\Scripts\python.exe -m piptools compile --generate-hashes --allow-unsafe --output-file requirements-tooling.lock requirements-tooling.txt
```

The application and development locks are shared by Windows and Linux. When they are
regenerated on Windows, keep `pywin32==312 ; sys_platform == "win32"` on the MCP
transitive dependency in both files. The repository hygiene test rejects an
unconditional Windows-only wheel before CI reaches installation.

## Run

Native development:

```powershell
.venv\Scripts\python.exe -m pip install --require-hashes -r requirements-tooling.lock
npm --prefix frontend run tauri:dev
```

Browser/container development:

```powershell
docker compose up --build
```

Open `http://127.0.0.1:5173`. Compose publishes only the Nginx frontend; the backend stays on the
private Compose network and accepts same-origin `/api/` traffic through that proxy. Uvicorn ignores
forwarded identity headers, so rate-limit identity cannot be selected with a direct
`X-Forwarded-For` value.

Manual backend and frontend:

```powershell
.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload --no-proxy-headers
npm --prefix frontend run dev
```

## Develop the CLI and MCP interface

The editable install above is the contributor workflow and registers `careeros` and `careeros-mcp`
from this checkout. It relies on the reviewed application dependency lock; do not run an
unconstrained install to make the command work. End users install a built wheel into a dedicated
Python environment, separately from the desktop app. The desktop installer does not install either
command on the system `PATH`. Agent configuration generated by the CLI uses `careeros` as its
command; run the client from the activated environment or replace it with the absolute path to this
environment's executable.

Use a disposable application-data directory for development. Create it through the normal desktop
bootstrap or test fixtures so it contains a migrated vault and installation secret. Close the
desktop app for authorization and MCP bootstrap:

```powershell
careeros --data-dir "C:\absolute\disposable\app-data" doctor
careeros --data-dir "C:\absolute\disposable\app-data" authorize `
  --username <test-user> --label local-development --days 1 `
  --scope system:read --scope applications:read
$env:CAREEROS_MCP_TOKEN = "<shown-once-token>"
careeros --data-dir "C:\absolute\disposable\app-data" status
careeros --data-dir "C:\absolute\disposable\app-data" mcp serve `
  --acknowledge-agent-disclosure
```

The desktop may run while the MCP process is idle. A tool call reacquires the lease and rechecks
the grant, so it returns `vault_busy` while the desktop is using the vault.

Do not automate the password prompt or put a grant token in a fixture, command transcript or
repository file. Tests issue grants directly against disposable databases and use the official MCP
client in memory and over a real stdio subprocess. Relevant focused checks are:

```powershell
.venv\Scripts\python.exe -m pytest tests/backend/automation -q
.venv\Scripts\python.exe -m ruff check backend/automation tests/backend/automation `
  backend/migrations/versions/f2a3b4c5d6e7_add_automation_grants.py
.venv\Scripts\python.exe -m mypy backend/automation --follow-imports=skip `
  --ignore-missing-imports --no-error-summary
```

Automation changes also require focused deletion and portability tests because complete erasure
removes grant rows and restore revokes active grants. A schema change still requires the Alembic
round trip below.

## Database changes

Import all mapped models through `backend/model_registry.py`. Create an Alembic revision, review it manually, and validate:

```powershell
.venv\Scripts\python.exe -m alembic upgrade head
.venv\Scripts\python.exe -m alembic downgrade -1
.venv\Scripts\python.exe -m alembic upgrade head
```

The downgrade round trip is a development/test check only. Production startup accepts forward
migrations to the single packaged head and deliberately refuses Alembic `downgrade` and `stamp`;
use the backup-protected startup runner and restore a verified backup for operational rollback.
Keep the SQLite data root on a local NTFS or POSIX filesystem because WAL and advisory migration
locks are not supported on network or cloud-synchronised filesystems. Never replace a migration
with a runtime `create_all` workaround.

On POSIX, source-runtime bootstrap requires the canonical `DATA_DIR` and every descendant through
the database parent to be owned by the effective user and repairs that in-scope chain to mode
`0700` before SQLite opens the vault. It never changes an ancestor above `DATA_DIR`, so that
deployment-owned ancestor must not be writable by other users. The main database and its
rollback-journal, WAL and shared-memory sidecars must be owned, ordinary, unaliased files and are
verified through no-follow descriptors before being repaired to `0600`. This boundary protects
against other OS users. It intentionally canonicalizes parent aliases and cannot isolate another
hostile process running as the same user; use the CareerOS vault lock for cooperating processes.
Runtime connection hooks revalidate these entries with `lstat` only: opening
and closing an unrelated descriptor could release POSIX `fcntl` locks held by another SQLite
connection in the process. Descriptor repair therefore happens only during pre-connection bootstrap
and the Alembic environment repeats that bootstrap after new-vault crash recovery. Startup validates
the canonical database location against `DATA_DIR` without filesystem writes, validates and acquires
the migration lock, reserves the private vault, and only then constructs or connects the migration
engine. Importing the readiness or application database modules does not create the vault or its
parent directories.

## Tests and quality

```powershell
.venv\Scripts\python.exe -m ruff check backend tests/backend scripts
.venv\Scripts\python.exe -m mypy backend scripts --ignore-missing-imports --no-error-summary
.venv\Scripts\python.exe -m pytest tests/backend -q --cov=backend --cov-branch --cov-fail-under=80
npm --prefix frontend run test:coverage
npm --prefix frontend run demo:install
npm --prefix frontend run test:e2e
npm --prefix frontend run lint
npm --prefix frontend run build
cargo fmt --manifest-path frontend/src-tauri/Cargo.toml --check
cargo clippy --manifest-path frontend/src-tauri/Cargo.toml --locked --all-targets -- -D warnings
cargo test --manifest-path frontend/src-tauri/Cargo.toml --locked
```

Tests deny public network access unless explicitly marked `live`. Use `TemporaryDirectory` for generated test data and never persist command output in the repository.

The portfolio media is also reproducible and uses only a disposable loopback vault. See the
[demo recording guide](demo.md) or run `npm --prefix frontend run demo:record`.
